# 懸念点（先に潰す。運用で埋めない）

remain / n10 が駐車された理由は「応募が下手」ではなく、**人間介入が多い時計進行**だった。全自動司令塔は、同じ穴をコードで塞ぐ。塞げない穴は人間の1クリックとして残し、宿題化しない。

## 致命（アカウントか円の正本が死ぬ）

| ID | 懸念 | いまの機械 |
|---|---|---|
| C1 | **公式応募 API が無い。** ログイン自動化・非公式 POST は規約第22条(12)(34) と AI ポリシーの迷惑行為に当たる余地 | 応募送信は人間。`CW: RESUME` は存在しない。スクレイパーは置かない |
| C2 | **実績捏造。** 完成納品 0 なのにポートフォリオや「あります」 | 事実カードの空欄は「無し」。`needs_portfolio` は納品 0 なら qualification 落ち |
| C3 | **カタログ円。** 公開 2,000円 / 応募画面 455円 / 100円を `approved_yen` に足す | キューは `approved_yen: null`。MEASURE と同じく source CW の画面未確定は拒否 |
| C4 | **remain / n10 の復活。** 閉じた ID への再応募、N=6 の分母、毎晩4件 | dump は `G_cw.txt` だけ。remain / n10 は開けるな。仕事 ID を Bot が足すな |
| C5 | **クライアント素材の外部AI無断投入** | 納品役は契約後。機密は外部へ投げない。AI 利用は隠さない |

## 層として残る制約（消えない）

1. 応募送信・契約・納品ボタン・出金は、公式 API が来るまで人間。
2. 納品物の品質と修正対応は、エージェントが増えてもクライアント合意が上。
3. 仮払い前に作業を始めるな（規約）。
4. 直接取引の誘導をするな。
5. GitHub cron は 1〜4 時間遅れる。応募締切のクロックに使うな。

## 最初の成功条件（円ではない）

1. `CW: GO` で Bot が `G_cw.txt` だけ開き、remain を開けない。
2. キューが空の日に、人間へ応募 ID を連発しない。
3. 資格判定が、顔出し・素材なし・実績必須・HALT を落とす。
4. カタログ円が CSV に入らない。
5. 初契約のあと、同時契約が 1 を超えて qualification しない。
